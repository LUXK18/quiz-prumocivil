Quero que você atue como arquiteto de software e desenvolvedor full-stack sênior e construa este projeto completo, com foco absoluto em simplicidade, performance, baixo consumo de recursos e facilidade de hospedagem em uma VM pequena.

Não quero apenas sugestões ou pseudocódigo. Quero que você desenvolva o projeto de forma incremental, criando a estrutura dos arquivos, código funcional, configuração, documentação e instruções de deploy.

# OBJETIVO DO APP

Construir uma aplicação web de "jornada interativa" baseada em etapas configuráveis.

O usuário entra em uma experiência com várias etapas, responde perguntas e avança até uma tela final com resultado e CTA.

Exemplo:

Entrada
  ↓
Pergunta
  ↓
Pergunta
  ↓
Pergunta
  ↓
Resultado
  ↓
CTA

O conteúdo das jornadas deve ser configurável, preferencialmente através de JSON.

A aplicação deve permitir criar diferentes jornadas sem alterar o código-fonte do frontend.

# PRINCÍPIO MAIS IMPORTANTE

O sistema precisa ser MUITO LEVE.

Ele será hospedado posteriormente em uma VM pequena.

Prioridades, nesta ordem:

1. baixo consumo de RAM
2. baixo consumo de CPU
3. frontend com bundle pequeno
4. poucas dependências
5. arquitetura simples
6. fácil manutenção
7. carregamento rápido
8. fácil deploy em Linux
9. boa segurança
10. boa experiência mobile

Evite soluções enterprise ou abstrações desnecessárias.

Não use Next.js, Nuxt, Angular ou frameworks pesados.

Não use bibliotecas grandes quando HTML/CSS/TypeScript nativo resolver.

Não use um banco complexo se SQLite resolver.

Não use Redis, filas, microsserviços ou infraestrutura distribuída.

Não crie complexidade pensando em uma escala que ainda não existe.

# STACK PREFERENCIAL

Antes de implementar, avalie esta stack:

Frontend:
- Vite
- TypeScript
- HTML/CSS
- JavaScript/TypeScript nativo
- sem React se não for realmente necessário

Backend:
- Go
- net/http ou framework extremamente pequeno somente se houver benefício real
- SQLite

Infraestrutura:
- Linux
- aplicação compilada em binário
- SQLite local
- frontend compilado como arquivos estáticos
- Caddy ou Nginx como reverse proxy, se realmente necessário
- systemd para manter o backend rodando

Idealmente quero:

1 processo do backend
+
arquivos estáticos do frontend
+
1 arquivo SQLite

Se for possível servir o próprio frontend estático pelo backend Go sem prejudicar a arquitetura, considere isso para reduzir ainda mais a infraestrutura.

Não use Docker como requisito obrigatório.

Docker pode ser fornecido apenas como opção adicional.

# ARQUITETURA CONCEITUAL

A aplicação gira em torno deste modelo:

Journey
  └── Steps
       └── Options

Uma Journey possui várias Steps.

Os tipos iniciais de Step são:

1. question
2. content
3. result

Uma pergunta possui dois layouts possíveis:

- list
- grid

Esses NÃO devem ser dois componentes de domínio diferentes.

Exemplo:

{
  "type": "question",
  "layout": "list"
}

ou:

{
  "type": "question",
  "layout": "grid"
}

Uma jornada pode ter aproximadamente esta estrutura:

{

  "name": "Diagnóstico principal",

  "branding": {

  "steps": [

      "id": "objetivo",

      "options": [
        {

          "label": "Economizar",
          "tags": ["price"]
        },
        {
          "id": "performance",
          "label": "Maior desempenho",
          "tags": ["performance"]
        }
      ]
    },

    {
      "id": "preferencia",
      "type": "question",
      "layout": "grid",
      "title": "Qual você prefere?",
      "autoAdvance": true,

      "options": [
        {
          "id": "a",
          "label": "Opção A",
          "image": "/assets/a.webp"
        },
        {
          "id": "b",
          "label": "Opção B",
          "image": "/assets/b.webp"
        }
      ]
    },

    {

Use esse JSON apenas como referência.

Melhore o schema se necessário, mas mantenha-o simples e legível.

# ENGINE DA JORNADA

O frontend deve possuir um Journey Engine pequeno responsável por:

- carregar a configuração
- identificar a etapa atual
- guardar respostas
- avançar
- voltar
- calcular progresso
- decidir resultado
- disparar eventos de analytics

Evite espalhar essa lógica pelos componentes.

Quero algo conceitualmente parecido com:

JourneyEngine
- currentStep
- answers
- progress
- next()
- previous()
- answer()
- getResult()

# PROGRESSO

Nunca quero configurar manualmente:

25%
50%
75%
100%

O progresso deve ser calculado automaticamente.

Exemplo:

currentStep / totalRelevantSteps

Adicionar ou remover etapas não pode exigir alterar percentuais.

# AUTO ADVANCE

Por padrão, perguntas de escolha única devem avançar automaticamente.

Fluxo:

usuário seleciona opção
↓
salva resposta
↓
dispara analytics
↓
pequeno feedback visual
↓
avança

Configuração:

"autoAdvance": true

Se:

"autoAdvance": false

mostrar botão:

Continuar

# VOLTAR

O usuário deve poder voltar para uma etapa anterior.

Ao alterar uma resposta anterior, o estado das etapas dependentes deve continuar consistente.

# RESULTADOS

Quero suporte inicial para resultados baseados em tags simples.

Exemplo de resposta:

{
  "id": "economia",
  "tags": ["price"]
}

Ao final podem existir resultados como:

{
  "id": "produto-economico",
  "when": ["price"]
}

Mantenha inicialmente o motor de regras muito simples.

Não quero criar um workflow engine.

Não implemente uma DSL complexa.

Se perceber que o sistema de tags é suficiente para o MVP, permaneça nele.

# ANALYTICS / GOOGLE TAG MANAGER

A aplicação deve possuir uma camada centralizada de analytics.

Não espalhe chamadas para dataLayer por dezenas de arquivos.

Crie algo como:

analytics.track(...)

Eventos padrão:

journey_started
step_viewed
step_answered
journey_completed
cta_clicked

Exemplo:

window.dataLayer.push({
  event: "step_answered",
  journey_id: "diagnostico-principal",
  step_id: "preferencia",
  step_index: 2,
  answer_id: "a"
})

O GTM Container ID deve ser configurável.

Não quero configurar manualmente um evento diferente para cada pergunta.

# PERSISTÊNCIA

Durante a jornada, as respostas podem inicialmente ficar no navegador.

Avalie usar:

sessionStorage

ou:

localStorage

Prefira sessionStorage caso seja suficiente.

Se o usuário atualizar a página durante a jornada, idealmente deve ser possível continuar de onde estava.

Permita limpar o estado quando a jornada terminar ou quando iniciar novamente.

# ADMINISTRAÇÃO

Preciso de um painel administrativo simples.

Não quero um page builder complexo.

O painel deve permitir:

- listar jornadas
- criar jornada
- editar jornada
- excluir jornada
- ativar/desativar jornada

Dentro de uma jornada:

- adicionar etapa
- editar etapa
- excluir etapa
- reordenar etapas

Campos básicos da etapa:

- título
- descrição
- tipo
- layout
- imagem
- opções
- autoAdvance

Para opções:

- label
- imagem
- tags

Resultado:

- título
- descrição
- imagem
- CTA
- regras simples

Para reordenação, não adicione uma biblioteca gigante de drag-and-drop.

Se uma implementação simples de subir/descer etapa for significativamente mais leve, prefira:

↑
↓

ao invés de drag-and-drop.
